# Self-hosted object-registration input staging

The registered v5 acquisition tree reaches `complete_object_registration` only
after the owner-only scaffold and the exact deployed Causal4D checkout validate.
The fixed registration requires four kinds of input:

1. the stable inventory serial attached to the exact physical sloth;
2. the frozen PhysTwin model identity and SHA-256;
3. the approved left-forepaw, right-forepaw, and upper-torso node sets; and
4. the unchanged scaffolded protocol and registration template.

The source-only anatomy review has already frozen items 2 and 3. The workflow
`Stage object-registration inputs on workstation2` copies the approved node-set
bytes into the authoritative v5 dataset and prepares an exact seal-command
template. It deliberately does not invent or infer item 1.

## Trigger

The registered maintainer opens an issue with the exact title:

```text
[self-hosted] stage Causal4D object-registration inputs
```

The issue body and labels are not executable inputs. The workflow runs on exact
reviewed `main` with a read-only repository token and no GitHub secrets.

## Admission checks

Staging is admitted only when:

- the deployed checkout is a clean ordinary Git repository at the exact issue
  event commit;
- hash-verified readiness derives exactly `complete_object_registration`;
- the action is nonphysical, nonautomatable, target-free, and method-preserving;
- `object_registration.json`, contact approval, slip evidence, method freeze,
  source-panel manifests, sessions, and confirmatory manifests are absent;
- the source-only anatomy approval validates; and
- its pending packet is blocked only by `physical_instance_serial`.

## Mutation and rollback

Only missing ordinary files below `contact_node_sets/` may be added. Existing
files must already have exact approved bytes. Every ordinary dataset file is
hashed before and after. Existing files may not change or disappear, and no
unexpected file may appear.

A failure removes every file added by the current run and verifies the original
dataset tree before returning an error. A successful rerun is idempotent.

## Remaining manual boundary

After staging, readiness intentionally remains:

```text
complete_object_registration
```

The workflow emits the exact command with one placeholder:

```text
<stable-physical-inventory-serial>
```

Only the stable inventory identifier physically attached to the exact sloth is
admissible. The logical object ID, a test fixture value, an issue number, or a
value inferred from prediction quality is not a substitute.

The registered operator must observe that serial and then execute the emitted
`object-registration-seal` command. This creates `object_registration.json`
exactly once. Contact-patch approval remains a separate later step.
